# AI Enricher — каталог mrmag.ru

Обогащение товаров через OpenRouter: обход разделов магазина, детерминированное
извлечение характеристик, SEO-материалы от модели и автофильтры.

На каждую категорию собираются два файла:

| файл | что внутри |
|---|---|
| `products_<id>.json` | массив товаров раздела (+ `enriched`, если прогон с ИИ) |
| `filters_<id>.json` | фильтры «Бренд» и «Цена», построенные из самих товаров |

`<id>` — id раздела магазина, он читается со страницы (`data-category`), а не
задаётся в коде.

Эти же два файла отдаёт интерфейс — кнопка **«2 файла»** рядом с выгрузками
JSON и TXT. Она не ждёт прогона: пара собирается и без ИИ, как `node catalog.js`.
Файлов всегда два на весь прогон: товары, загруженные по адресу фида, лежат
вперемешку по категориям, и такой набор склеивается в одну пару
`products_all.json` + `filters_all.json` — id одного из разделов в имени соврал
бы про остальные. Насыщать
такой фид целиком обычно не нужно: шаг 2 показывает категории, которые нашлись
в загруженном (файл с диска, адрес фида или обход раздела), со счётчиком по
каждой — выбранная остаётся, остальные в прогон не идут. Сколько обработать —
пять частых чисел кнопками и поле рядом для своего. Имена и форма
записей те же, что у CLI, поэтому файлы взаимозаменяемы:

* в `products_<id>.json` попадают **все** загруженные товары, у необработанного
  `enriched: null` — как в файле из CLI. Соседняя выгрузка «JSON» наоборот
  показывает только прогон;
* фильтр берётся из ответа обхода и описывает **весь раздел**, а не загруженное
  окно. Считает его сервер той же `buildFilters`, что пишет файл в CLI —
  копии этой логики в браузере нет.

## Выгрузка «JSON v2»

Кнопка **«JSON v2»** рядом с «JSON» и «TXT» отдаёт формат импорта по трём
файлам: `categories_v2.json` на все разделы плюс одна пара
`filters_v2_<id>.json` + `products_v2_<id>.json` на весь прогон — товары всех
разделов идут вместе, а `<id>` становится `all`, когда разделов больше одного.
Диапазоны фасетов при этом считаются по всему набору сразу: посчитай их по
разделам и склей файлы потом — у товара остался бы диапазон своего раздела,
которого нет в общем списке фасетов.

```json
// categories_v2.json
{ "categories": [ { "id": 523, "name": "Холодильники" } ] }

// filters_v2_523.json — все фасеты checkbox, числовые свёрнуты в диапазоны
{ "filters": [
  { "name": "Цвет",          "value": ["белый", "серебристый", "чёрный"] },
  { "name": "Объем общий, л", "value": ["150-200", "200-250", "250-300"] },
  { "name": "Цена, ₽",        "value": ["0-25000", "25000-50000", "50000-75000"] }
] }

// products_v2_523.json
[ { "id": 296646, "name": "Холодильник LG GA-B419SQGL",
    "meta_keywords": "холодильник, LG, No Frost, …",
    "description_html": "<p>…</p><ul><li>Объем общий: 310 л</li></ul><p>…</p>",
    "filters": { "Цвет": "белый", "Объем общий, л": "300-350", "Цена, ₽": "25000-50000" } } ]
```

Что важно про этот формат:

* имя фасета и значение у товара считает одна функция `buildV2` на сервере.
  Разойдись они хоть в округлении — товар не попал бы ни в один свой фильтр, и
  раздел молча отдал бы пустую выдачу. Копии этой логики в браузере нет;
* имена фасетов собираются из ключей схемы: `объем_общий_л` → «Объем общий, л»,
  `скорость_отжима_об_мин` → «Скорость отжима, об/мин». Единица уходит и в имя
  фильтра, и в строку характеристики («Объем общий: 310 л»);
* цена — такой же checkbox-фасет «Цена, ₽» диапазонами; она идёт последней
  после характеристик. Цена `0` считается отсутствием цены (как в
  `buildFilters`) и в фильтр не попадает — иначе весь раздел без цены осел бы в
  первом диапазоне;
* диапазоны — круглым шагом ~1/8 разброса раздела (1/2/2.5/5/10 × 10^k). Пока
  разных значений ≤ 6 или шаг выходит в единицу на целых числах, значения
  перечисляются как есть: «39-40» ничего не сворачивает;
* `да`/`нет` из схемы становятся «Есть»/«Нет» — и в фильтре, и в описании;
* `description_html` — абзац описания, список точных характеристик, список
  плюсов (`bullets` от модели) и закрывающий абзац. Плюсы отдельным `<ul>`:
  в первом списке значения из характеристик, во втором текст модели;
* идут **только обработанные** товары: без `enriched` у товара нет ни
  `description_html`, ни характеристик. Полный список раздела с
  `enriched: null` — это выгрузка «2 файла».

Тот же формат собирается из готового файла CLI: `buildV2` принимает массив в
форме `products_<id>.json`.

| раздел | id | товаров на сайте |
|---|---|---|
| [Холодильники](https://mrmag.ru/shop/kholodilniki) | 523 | 256 |
| [Стиральные машины](https://mrmag.ru/shop/stiralnye_mashiny) | 467 | 153 |

Числа — текущий остаток раздела. 259 и 160 из первоначальных требований — это
13×20 и 8×20, то есть счёт по страницам листинга.

## Отбор товаров перед прогоном

Список товаров в середине экрана — это ещё и отбор. **Прогон идёт по тому, что
видно**: и оценка стоимости в шаге 3, и кнопка запуска показывают уже суженное
количество, а не весь загруженный список.

* **«Без данных N»** — товары, из которых модели нечего извлекать: нет ни
  `description`, ни `annotation`, либо текст короткий и ни одной характеристики
  в нём не распознано. В строке товара видно причину. Считает это не браузер, а
  `POST /api/quality` — та же `isEnrichable`, которой `/api/enrich` потом
  пропускает товар. Разойдись они, фильтр показывал бы одно, а прогон делал
  другое. Если в названии есть артикул, в строке дописано «поищем описание в
  сети» — такой товар до модели ещё дойдёт, см. [поиск в
  сети](#товар-без-описания-поиск-в-сети);
* **дата импорта** — пара полей «с … по …» под фильтрами. Имя поля не вбито в
  код: берётся первое найденное у загруженных товаров из
  `imported_at`, `import_date`, `date_import`, `imported`, `created_at`,
  `date_created`, `updated_at`, `modified`, `date` (ISO-строка или unix-время).
  Поля нет — строка не показывается вовсе; какое нашлось и за какой период
  вообще есть товары, написано под ней. Обе границы включительно, товары без
  даты в заданный диапазон не попадают;
* фильтры складываются: «Без данных» + диапазон дат — это «обогатить то, что
  приехало в июне и приехало пустым».

Повторный запуск заменяет результаты **только отобранных** товаров — за
остальные уже заплачено, и они остаются на месте.

## Быстрый старт

Нужен Node ≥ 20. Зависимостей нет.

```bash
cp .env.example .env    # вписать OPENROUTER_API_KEY и APP_PASSWORD
```

Собрать каталог и фильтры **без ИИ** (бесплатно, только обход сайта):

```bash
node catalog.js
```

Прогон с обогащением по одному разделу:

```bash
OPENROUTER_API_KEY=sk-or-v1-... CATEGORY=stiralnye_mashiny node enricher_mrmag.js
```

Веб-интерфейс:

```bash
OPENROUTER_API_KEY=sk-or-v1-... APP_PASSWORD=пароль node server.js
```

Node ≥ 22 умеет читать `.env` сам:

```bash
node --env-file=.env server.js
```

## Как это работает

Листинг раздела уже содержит sku, название, цену, наличие, картинку и **бренд**
(`class="mr-brand"`) — поэтому фильтр строится без единого лишнего запроса и по
классификации самого магазина, а не по догадке из названия. Страницы листинга
читаются всегда все: фильтр описывает раздел, а не то окно, которое обрабатывают.

Описания листинг не отдаёт. Их источник:

1. фид `products.json` — для холодильников там есть все sku раздела, это экономит
   250+ запросов;
2. страница товара — по одному запросу (стиральные машины, в фиде их нет).

Таблица «Характеристики» со страницы товара разворачивается в `annotation`
строками «подпись - значение» — ровно как это делает сам фид. Поэтому весь
дальнейший разбор один и тот же независимо от источника.

Страницы кэшируются в `PAGE_CACHE_DIR` на сутки, между запросами к сайту пауза
`CRAWL_GAP_MS` (~4 запроса в секунду).

### Товар без описания: поиск в сети

Часть карточек пуста и в фиде, и на самой странице магазина — ни описания, ни
таблицы характеристик (в холодильниках это 41 товар из 1654). Раньше такой
товар уходил в «пропущен»: модели нечего было показать. Но сам товар
существует, и та же модель описана у производителя и других продавцов.

Поэтому при пустой карточке `ensureSource` (catalog.js) ищет её в сети:

1. из названия берётся артикул (`modelToken`): «Холодильник LG GC-Q247CAMT» →
   `GC-Q247CAMT`. Артикула в названии нет — искать не по чему, товар
   пропускается как раньше;
2. запрос уходит в поисковик без ключа и без JS: свой `SEARCH_URL`, затем
   DuckDuckGo (html и lite) и Mojeek. Первый, кто ответил ссылками, и
   используется — за частые запросы поисковик отдаёт заглушку вместо выдачи;
3. из выдачи берётся до `WEB_LOOKUP_TRIES` страниц, по одной на домен;
4. **страница принимается, только если на ней есть артикул** — иначе в карточку
   уедут характеристики соседней модели. Это единственная проверка личности
   товара, поэтому она строгая: не совпало — берём следующую страницу;
5. таблица характеристик разворачивается в `annotation` строками
   «подпись - значение» — тем же видом, что даёт фид, поэтому дальше работает
   всё то же самое: `extractFacts`, гейт, промпт, сверка;
6. торговые фразы чужого магазина («купить», «доставка», цена в рублях) в
   описание не попадают;
7. локальные и служебные адреса из выдачи (`127.0.0.1`, `169.254.169.254`,
   `10.*`, `*.local`) не читаются вовсе — иначе подсунутая ссылка превратила бы
   обогащение в чтение внутренней сети и метаданных облака. Снимается
   `WEB_ALLOW_LOCAL=1`, и нужно это только тестам.

Атрибуты магазина при этом не трогаются: они задают фасеты каталога, и
подмешивать в них чужую таблицу нельзя — «спор каталога с самим собой» должен
оставаться спором каталога.

Адрес найденной страницы виден везде, где виден результат: `source_url` в
ответе `/api/enrich`, строка «описание добрано из сети: домен» в карточке,
`source_url` в JSON- и TXT-выгрузках и в `_meta` записей CLI. Откуда взялся
текст — видно, а не подразумевается.

Отключается `WEB_LOOKUP=0`: тогда пустая карточка снова просто пропускается.

### Схема на категорию

У холодильника и телевизора общего — только габариты и вес. Поэтому набор полей,
промпт и разбор фактов свои на каждую категорию (`SCHEMAS` в `lib.js`). Схема
выбирается по `category` товара: сначала точное совпадение по slug, id или
названию, иначе по вхождению в путь категории (`Техника для дома/Холодильники`
даёт схему холодильников — самый точный раздел стоит в пути последним).

Категорий восемнадцать: шестнадцать разделов магазина плюс два подраздела,
которые обходятся отдельно (`kholodilniki`, `stiralnye_mashiny`). Неизвестная
категория получает `GENERIC_SCHEMA` — общие поля. Раньше её роль играл
холодильник, и телевизор получал в промпте объём морозильной камеры.

Схема — это декларация, а не текст промпта:

```js
fields: [
  ['тип_товара', 'str'],                       // строка
  ['диагональ_дюйм', 'num'],                   // число
  ['разрешение', ['HD', 'Full HD', '4K UHD']], // значение из списка → фасет
],
labelKeys: ['вес_кг', 'диагональ_дюйм'],       // как искать это в тексте
ranges:    { диагональ_дюйм: [1, 120] },       // диапазон правдоподобия
```

Промпт собирается из неё целиком, поэтому новая категория — это запись в
реестре, а не новый текст на 200 строк.

### Значения из списка — это фильтр сайта

Поле с массивом допустимых значений питает фасетный фильтр витрины. Модель
обязана взять значение точно из списка; `normalizeResponse` приводит регистр и
очевидные синонимы («есть» → «да»), а всё остальное обнуляет и пишет в
`warnings`. Одно «фронтальный тип загрузки» вместо «фронтальная» — это лишний
пункт в фильтре, по которому висит один товар.

### Что модель возвращает

| поле | что это | длина |
|---|---|---|
| `specs` | характеристики по схеме категории | — |
| `seo_title` | тег `<title>` | 30–60 |
| `h1` | заголовок страницы | 10–70 |
| `meta_description` | мета-описание | 120–170 |
| `short_description` | подпись в плитке каталога | 40–200 |
| `seo_description` | основной текст карточки, три абзаца | 900–2200 |
| `bullets` | преимущества, каждое из конкретного значения | 3–6 шт. |
| `synonyms`, `search_aliases`, `seo_keywords` | поиск и продвижение | 4–10 шт. |

Порог основного текста зависит от материала: если в `specs` заполнено меньше
пяти полей, хватает 400 символов. Требовать 900 там, где о товаре известны бренд
и цвет, — значит требовать домыслов.

Длины проверяются после ответа: выход за границы попадает в `seo_issues`
отдельно от `warnings`. Расхождение с текстом — повод не верить значению,
длинный title — повод причесать текст, и мешать это в одну кучу нельзя.

### Факты, а не только модель

Из карточки детерминированно извлекается то, что берётся однозначно. Эти факты
работают в три стороны: уезжают модели в промпте как проверенные значения,
сверяют её ответ (`warnings`) и добирают поля, которые она оставила `null`
(`filled_from_text`).

Источников два. **Текст** (`description` + `annotation`) даёт точные значения.
**Атрибуты магазина** — те же поля, но структурные, по ним работает фильтр
сайта, и модель их тоже видит. Половина значений там не характеристика, а
корзина фильтра: `Высота холодильника: От 181 до 190 см` подставить в поле
нельзя, а проверить попадание можно. Поэтому атрибут даёт либо факт, либо
интервал, и в расхождения попадает только выход за границы — с тем же допуском
на округление, что и у чисел из текста.

Значение с двумя вариантами сразу — тоже корзина фильтра, а не характеристика:
`Система разморозки: Капельная система/ручная` (75 холодильников из 256) не
говорит, какая из двух, и фактом не становится.

Когда текст и атрибут спорят, не утверждается ничего — ни то, ни другое. В
каталоге на 256 холодильников таких карточек четыре: товар высотой 194,7 см
лежит в полке «От 181 до 190 см». Это ошибка каталога, и разрешать её догадкой
в свою пользу нельзя — иначе проверка обвинит модель за верный ответ.

Молча такой спор не проглатывается: он приходит из `/api/quality` в поле
`conflicts` рядом с вердиктом «без данных», а в интерфейсе получает свой фильтр
**«Ошибки каталога»** и блок в карточке с обеими сторонами спора. Считается это
из исходных данных, поэтому видно **сразу после загрузки товаров — до прогона и
без единого запроса к модели**. Не путать с фильтром «Расхождения»: там модель
спорит с источником, здесь источник спорит сам с собой, и чинить это в магазине.
В выгрузку обогащённого товара то же самое уезжает полем `source_conflicts`.

Поэтому ложный факт дороже пропущенного. Отсюда диапазоны правдоподобия и отказ
доверять подписи осей, которая их не прошла.

По той же причине «самое большое число тройки — высота» стало свойством
категории (`tallest`), а не общим правилом: у холодильника это так, у
телевизора наибольшая сторона — ширина. Там, где правило не работает, тройка
уезжает модели неразложенной по осям.

## Переменные окружения

Все — в [`.env.example`](.env.example) с пояснениями. Главные:

| переменная | зачем |
|---|---|
| `OPENROUTER_API_KEY` | обязательна; остаётся на сервере |
| `APP_PASSWORD` | пароль на интерфейс и API; пусто = сервер открыт |
| `HOST` / `PORT` | `0.0.0.0` нужен в контейнере |
| `ALLOWED_HOSTS` | кому разрешён прокси `/api/product` |
| `CATEGORY` | раздел для CLI: slug, id, название или адрес |
| `MISMATCH_POLICY` | `flag` (пометить) или `strict` (обнулить спорное поле) |

## Маршруты

| маршрут | назначение |
|---|---|
| `GET /healthz` | проба живости, **без** аутентификации |
| `GET /api/models` | модели OpenRouter с ценами (кэш 5 минут) |
| `GET /api/categories` | разделы и поля схем |
| `GET /api/catalog?category=…&limit=N` | обход раздела: товары + автофильтры (+ готовый `filters_file`) |
| `POST /api/filters` | фильтры по переданному списку товаров |
| `POST /api/quality` | вердикт `isEnrichable` по списку товаров: `{ quality:[{ok,reason}] }` |
| `GET /api/product?url=…` | прокси к JSON-каталогу по списку хостов |
| `POST /api/enrich` | обогащение одного товара; у товара без своего текста в ответе `source_url` — откуда взято описание |

## Деплой

```bash
cp .env.example .env    # APP_PASSWORD задать обязательно
docker compose up -d --build
docker compose logs -f
```

Контейнер называется `ai-enricher`, внутри слушает 3000. Наружу его публикует
nginx-proxy-manager: он подключён к сети `enricher-docker_default` и ходит по
имени контейнера, поэтому порт на хосте открыт только на `127.0.0.1:3004` — для
проверок с самого сервера. Имя compose-проекта закреплено (`name:`), иначе сеть
переименуется вслед за каталогом и NPM ответит 502.

Если NPM пересоздадут его собственным compose, подключение к сети слетит:

```bash
docker network connect enricher-docker_default nginx_proxy_manager
docker restart nginx_proxy_manager
```

Перезапуск обязателен — nginx кэширует резолв и без него держит «host not found».

Что важно перед публикацией:

1. **Задать `APP_PASSWORD`.** `/api/enrich` тратит деньги, открытый доступ к нему
   — открытый доступ к вашему счёту. Без пароля сервер работает, но громко
   предупреждает при старте.
2. **TLS терминирует nginx-proxy-manager.** Basic-пароль по HTTP уходит
   открытым текстом, поэтому домен должен быть только на https.
3. **Том для кэша.** `/data` в контейнере: без него каждый перезапуск обходит
   раздел заново.
4. **Поднять `proxy_read_timeout` в NPM.** По умолчанию nginx ждёт ответа минуту
   и обрывает запрос страницей «504 Gateway Time-out». Один товар в
   `/api/enrich` — это до трёх минут: генерация описания на 900–1800 символов
   занимает больше минуты сама по себе, плюс до трёх попыток при сбое сети.
   В хосте NPM → Advanced → Custom Nginx Configuration:

   ```nginx
   proxy_read_timeout 300s;
   proxy_send_timeout 300s;
   ```

   Без этого прогон сыплется 504-ми на длинных товарах, причём деньги за них
   уже списаны: сервер дописывает ответ модели в пустоту.
5. **Обновить курс.** `RUB_PER_USD` и `RUB_RATE_DATE` вбиты вручную и в отчётах
   печатаются вместе с датой.

`SIGTERM` дожидается текущих запросов (до 10 с), `HEALTHCHECK` в образе ходит на
`/healthz`, `restart: unless-stopped` поднимает после сбоя.

## Если до OpenRouter не достучаться

Признак: TCP до `openrouter.ai:443` открывается (`nc -z` проходит), а TLS-рукопожатие
виснет, `fetch` падает с `UND_ERR_CONNECT_TIMEOUT`. При этом до `api.github.com`
и `cloudflare.com` TLS проходит. Это блокировка по SNI на стороне провайдера, и
настройками контейнера она не лечится — нужен выход наружу через прокси.

Проверить за минуту:

```bash
docker exec ai-enricher node -e "
const tls=require('tls');
for (const h of ['openrouter.ai','api.github.com','cloudflare.com']) {
  const s=tls.connect(443,h,{servername:h},()=>{console.log(h,'→ ok');s.end()});
  s.setTimeout(12000,()=>{console.log(h,'→ ЗАВИС');s.destroy()});
  s.on('error',e=>console.log(h,'→',e.message));
}"
```

Сначала исключите подмену DNS — она даёт ровно ту же картину:

```bash
docker exec ai-enricher sh -c 'nslookup openrouter.ai; nslookup openrouter.ai 1.1.1.1'
```

Настоящие адреса — `8.47.69.6` и `8.6.112.6`. Если свой резолвер отдаёт что-то
другое (например `8.47.69.0`, сетевой адрес той же подсети), это подмена:
заглушка принимает TCP, поэтому `nc -z` показывает «порт открыт», а TLS в неё
уходит без ответа. В `docker-compose.yml` для этого уже прописаны публичные
резолверы `1.1.1.1` и `8.8.8.8`.

На сервере skyputh было именно это: ответы приходили с обнулённым последним
компонентом адреса (`8.47.69.6` → `8.47.69.0`), причём одинаково через любой
резолвер — подмена прозрачная. TLS до правильных адресов при этом проходит,
поэтому в `docker-compose.yml` они закреплены через `extra_hosts`.

Проверить, что закреплённые адреса ещё живые:

```bash
docker exec ai-enricher node -e "
const tls=require('tls');
for (const ip of ['8.47.69.6','8.6.112.6']) {
  const s=tls.connect(443, ip, {servername:'openrouter.ai'}, ()=>{console.log(ip,'ok'); s.end()});
  s.setTimeout(12000,()=>{console.log(ip,'ЗАВИС'); s.destroy()});
  s.on('error',e=>console.log(ip,e.message));
}"
```

Сервер печатает при старте, куда резолвится `openrouter.ai` — если там снова
адрес на `.0`, значит `extra_hosts` не применились.

Если и с правильным адресом TLS виснет — тогда режут по SNI, и лечение одно: HTTP-прокси в `.env`:

```
HTTPS_PROXY=http://user:pass@proxy.example.com:3128
NO_PROXY=mrmag.ru,localhost,127.0.0.1
```

`NODE_USE_ENV_PROXY=1` в образе уже стоит, поддержка встроена в Node 24.
`mrmag.ru` из прокси исключён: это лишний крюк и лишняя точка отказа.

### 403 «Access denied by security policy»

```
server: cloudflare
cf-ray: ...-DME
{ "success": false, "error": "Access denied by security policy." }
```

Cloudflare перед OpenRouter блокирует по географии адреса. Приходит на публичный
`/api/v1/models` и **без ключа** — то есть ключ ни при чём. С сети другой страны
тот же запрос отдаёт 200 (узел `-AMS` вместо `-DME`).

Лечится только выходом через сеть, которая не заблокирована. В `.env`:

```
SOCKS_PROXY=tg://socks?server=1.2.3.4&port=3443&user=логин&pass=пароль
HTTPS_PROXY=http://127.0.0.1:18080
```

Строки именно две. `SOCKS_PROXY` поднимает мост, `HTTPS_PROXY` направляет в него
`fetch` — и вторая обязана существовать **до старта процесса**: Node фиксирует
настройки прокси не позже первого запроса, а разные версии делают это в разный
момент. Выставленная из кода переменная на Node 24 уже не подхватывается, и
запрос уходит мимо моста. Сервер это заметит и напишет при старте, чего не
хватает.

SOCKS5 Node сам не понимает, поэтому `socks.js` поднимает на localhost
крошечный HTTP-прокси и уводит каждый CONNECT в SOCKS. Трафик остаётся сквозным
TLS: владелец прокси видит имя хоста, но не содержимое, и ключ OpenRouter ему
не достаётся. HTTP-прокси задаётся проще — `HTTPS_PROXY=http://...`, мост не нужен.

`mrmag.ru` идёт мимо прокси (`NO_PROXY`): гонять российский каталог через
заграничный канал незачем.

Ни `extra_hosts`, ни смена резолвера здесь не помогают — это уже не сеть,
а решение принимающей стороны.

Пока прокси нет, прогон делается с машины, у которой доступ есть:

```bash
CATEGORY=kholodilniki node enricher_mrmag.js
scp products_*.json filters_*.json сервер:/opt/mrmag-enricher/
```

## Обновление уже развёрнутой версии

Пакет релиза собирается в `dist/`:

```bash
tar -czf dist/enricher-1.1.0.tar.gz package.json lib.js catalog.js server.js \
  enricher_mrmag.js index_final.html test*.mjs smoke.mjs \
  Dockerfile docker-compose.yml .dockerignore .env.example README.md
```

После распаковки на сервере — обязательно прогнать проверку живой установки:

```bash
node smoke.mjs https://ваш-адрес admin:пароль
```

### Что изменилось с 1.0.0

| было | стало | что делать |
|---|---|---|
| товары из фида `products.json` (1654 холодильника) | обход разделов сайта: 523 и 467 | ничего, `CATEGORY` по умолчанию `kholodilniki` |
| одна схема полей на всё | схема на категорию | ничего |
| ledger `mrmag_enriched.jsonl` | `enriched_<id>.jsonl` | **см. ниже** |
| выгрузка `mrmag_enriched.json/.txt` | `products_<id>.json` + `filters_<id>.json` | забрать новые файлы |
| сервер без аутентификации | Basic по `APP_PASSWORD` | задать пароль |

**Про повторную оплату.** Прежний прогон копился в `mrmag_enriched.jsonl`. Новая
версия ведёт `enriched_<id>.jsonl`, и если начать с чистого файла, все уже
обогащённые товары будут оплачены заново. CLI это заметит и подскажет; чтобы
продолжить со старого журнала:

```bash
OUT=mrmag_enriched.jsonl CATEGORY=kholodilniki node enricher_mrmag.js
```

### Новые переменные окружения

`APP_USER`, `APP_PASSWORD`, `HOST`, `PAGE_CACHE_DIR`, `PAGE_CACHE_TTL_MS`,
`CRAWL_GAP_MS`, `OUT_DIR`, `CATEGORY`, `MODELS_TTL_MS`, `MAX_PROXY_BYTES`,
`WEB_LOOKUP`, `WEB_LOOKUP_TRIES`, `SEARCH_GAP_MS`, `SEARCH_GIVE_UP`, `SEARCH_URL`,
`WEB_ALLOW_LOCAL`.
Все необязательные, кроме `APP_PASSWORD` — без него сервер работает, но открыт.
Старый `.env` продолжит работать; сверьтесь с `.env.example`.

### Кэш страниц

`PAGE_CACHE_DIR` (по умолчанию `.page_cache`) должен пережить перезапуск, иначе
раздел обходится заново: 13 запросов для холодильников и 168 для стиральных
машин. В контейнере это том `/data`.
